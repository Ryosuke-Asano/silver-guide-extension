# 行政手続き支援の実用性レビュー

## 目的と方法

初めて使う人が、元のページの項目名と説明を確かめ、次に操作する欄を見つけ、ページのエラー通知から戻れるかを開発者が確認した。対象は、大きい文字・キーボード操作を含む既存の Silver Guide の利用者像である。実際の高齢者を対象にした利用者テストではない。

2026-10-06 に公式の公開ページを GET で読み取り、静的 DOM の項目構造とリンク先を確認した。入力・選択・送信・同意・ログインは行っていない。実拡張の操作は、構造だけを反映した架空の localhost fixture と隔離プロファイルで確認した。公開ページそのものに拡張を注入した動作確認や、認証後の申請画面の検証とは区別する。

## 公開ページで観察した問題

| ページと方法 | 公開構造の観察・旧実装の結果と予測 | 今回の改善の対象 |
| --- | --- | --- |
| [横浜市・住民票オンライン申請案内](https://www.city.yokohama.lg.jp/kurashi/koseki-zei-hoken/todokede/koseki-juminhyo/shoumei/jyuminhyou/online.html)、公開 GET と静的 DOM | 本文に申請欄がなく、サイト上部の検索欄だけが存在する。label は画像の alt「サイト内検索」。旧コードでは画像の項目名を読めず、検索欄が最初の入力候補になる構造だった。 | 画像による公開ラベルを読めるようにする。検索やサイト共通の欄を初期案内の対象と区別し、利用者が直接選んだときは共通欄として支援する。 |
| [e-kanagawa・システム操作に関する問い合わせ](https://dshinsei.e-kanagawa.lg.jp/140007-u/inquiryForm/inputInquiryForm_initDisplay.action)、公開 GET と静的 DOM・欄解析 | 電話番号の可視 label は「電話番号」だが、ARIA の項目名は入力例の文章。旧解析の項目名がその入力例になり、表示ロジックからヒントのタイトルも説明文になると分かった。必須表示は dt 内の別 span にあり、native required / aria-required にはない。 | 可視の項目名と読み上げ用の名前を区別する。項目見出しにある公開必須表示を補足し、ブラウザの必須属性や入力完了の判定とは混同しない。 |
| [デジタル庁・ご意見とお問い合わせ](https://www.digital.go.jp/contact)、公開 GET | 制度によって FAQ・フォーム・チャットの窓口が異なる。 | 未確認の窓口を一律に推薦しない。汎用支援は公開項目の読み取りに限定し、制度固有の導線は確認済みガイドで扱う。 |
| 横浜市の本文リンクと [公式 FAQ](https://www.city.yokohama.lg.jp/kurashi/koseki-zei-hoken/todokede/koseki-juminhyo/shoumei/faq.html) の GET | 従来の「よくある質問」リンク先は総合案内だった。現行本文は別の FAQ ページを案内している。 | ガイドの FAQ リンクを現行の公式リンクに合わせる。 |

氏・名の fieldset 文脈は既に取得できたため変更しない。入力欄の近くにある任意の段落をまとめて読んだり、エラー原文を転載したりする機能は追加しない。説明が構造上結ばれていない欄では、利用者に元のページの説明を確認してもらう。

## 架空フォームでの操作レビュー

| フロー | 確認する実用性 | 観察と改善の範囲 |
| --- | --- | --- |
| 支援開始 → 項目の発見 → native label / radio / select / 添付欄 | 最初の候補の分かりやすさ、フォーム境界、入力や選択を変えない移動 | 検索を申請欄と混同しない初期案内。現在の項目名・位置・公開形式を表示する。 |
| キーボードの通常 Tab、大きい文字、画面幅の変更、短い次画面 | 現在操作する欄がパネルに隠れず、元のフォームを使えること | PR #1 の追加検証で重なりを再現し、Tab / resize 後の配置と短いページの上下配置を修正した。 |
| ARIA のエラー表示 → 最初のエラー項目へ、native invalid 通知 | 利用者が修正箇所へ戻り、エラー原文の個人情報を転載しないこと | ページが明示した項目へ戻る。値の検証・修正済み判定や送信はしない。 |
| 条件付き欄の表示 → DOM による次の手順 | 古い欄や隠れた手順に案内しないこと | 表示中の欄・手順だけを再解析する。実申請の画面遷移は利用者自身の操作とする。 |
| 入力のヒント → readonly / password / 独自入力欄 | 直前のヒントを別の欄の説明として見せず、移った欄を操作できること | 対象外の入力欄へフォーカスしたときは前のヒントを解除する。解除後のパネルが欄に重なる回帰も実測し、配置だけを対象欄の矩形に合わせる。入力値は取得しない。 |
| 用語説明を開く → 文字の大きさ・原文表示を変更 | 開いている説明に設定が反映され、キーボード操作を失わないこと | 説明の表示を更新し、操作中のフォーカスを保つ。 |

## 評価の限界

複数の代表的な構造で「どの欄か」「公開されている形式は何か」「どのエラー欄へ戻るか」を確認する支援として評価する。資格・制度の解釈、記入内容の正しさ、提出可否、申請完了を判断する機能ではない。

サイト側がラベル・ランドマーク・エラー状態を明示しない場合は識別できないことがある。サイト共通の欄の判定も HTML の公開構造に限る。iframe、サイトの Shadow DOM、独自ウィジェット、PDF、認証後の画面、音声読み上げの実際の発声は引き続き検証が必要。極端に狭い画面で空き領域が不足する場合はパネルを手動で縮小する。フォームから支援パネルへキーボードで戻る操作の負担も今後の課題として残る。

再現可能なテストと結果は [検証記録](qa.md)、対応範囲は [フォーム支援](form-support.md) にまとめる。PR #1 の基盤改善と、ここで観察した問題への後続改善は別の変更としてレビューする。
