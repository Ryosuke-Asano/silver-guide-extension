# ウェブ上のPDF記入・添付連携を拡張側へ集約する

2026年10月28日。デモページの専用ボタン・固定URL・windowメッセージへの依存を廃止し、Silver Guide自身が通常のウェブページでPDFを検出する。

## 利用者の流れ

1. PDFリンクや埋め込みPDFの横に、拡張が「Silver Guideで記入」を表示する。選択済みPDFには「選択したPDFに記入」を表示する。元のリンクやファイル選択はそのまま使える。
2. ボタンを押すと、そのPDFを専用タブへ取り込む。添付先が一意に決まり、既存ファイルを無断で置き換えない場合は、最初の質問へ直接進む。
3. 添付先が複数、または既存ファイルの置き換えが必要な場合は、欄の公開ラベルから選ぶ。添付欄がなければ通常のPDF保存へ進む。
4. 「入力を完了」で、選んだ元の欄へ検証済みPDFを戻す。通常サイトでは添付までを既定にし、送信ボタンの操作も必要なら、表示されたボタン名と「入力完了後に実行する」を選ぶ。
5. 元サイトの確認・認証・受付結果は、そのサイトの画面で扱う。サイト固有の複数段階の操作は、拡張内のアダプターで追加する。

PDFを見つけただけでは取得・添付・送信を行わない。利用者が拡張の記入ボタンを押したPDFだけを扱う。

## 責務と境界

| 層 | 実装 | 責務 |
| --- | --- | --- |
| 検出 | `src/features/pdf/detection.ts` | URL末尾、MIME指定、download名、object／embed／iframe、選択済みFileからPDF候補を見つける。公開ラベルとフォームの関連から添付候補を列挙する |
| ページ内制御 | `src/features/pdf-handoff.ts` | 拡張のボタン、動的DOMの監視、資料・文書・実DOM要素への結び付け、元欄へのFile設定とinput／changeイベント、二重実行の防止 |
| タブの起動 | `src/background/v3.ts` | 認証したcontent scriptのタブから専用タブを開く。PDFや送信待ち状態をバックグラウンドに保持しない |
| 受け渡し・取得 | `src/shared/pdf-handoff.ts` | バージョン付きメッセージ、20MiB上限、ストリームの上限検査、PDF形式の検査、結果の型 |
| 記入画面 | `src/apps/workspace/usePdfHandoff.ts` | PDFの取り込み、添付先選択、送信操作の選択、既存PDFエンジンへの接続、元タブへの復帰 |
| 標準フォーム | `src/features/pdf/submission.ts` | 指定したsubmitterと送信先の照合、サイトのchange処理の待機、標準の入力検証とrequestSubmit |
| サイト固有手順 | `src/adapters/sites/` | サイトの一致条件と確認画面以降の操作。共通の検出・取得・PDF処理を変更せず追加できる |

図書館デモのアダプターは複数段階の手順の実装例であり、汎用機能を有効にする条件ではない。デモのHTMLとJavaScriptは、通常のダウンロード・ファイル添付・内容確認・完了操作へ戻す。拡張との通信機能は不要。

## 取得と権限

同一オリジンのPDFは、元ページのcontent scriptからセッションを使って取得する。別オリジンや元ページから取得できないPDFは、対応する記入タブが、既に許可された配布元へのホストアクセスを確認して取得する。追加の権限を自動取得しない。content scriptと拡張ページで取得可能な範囲が異なる点は、[Chromeのネットワーク仕様](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)に従う。

取得はクリック後のみ、GET、20秒のタイムアウト、20MiBのストリーム上限とする。別オリジンへの取得には認証Cookieを添付しない。リダイレクトは自動追跡しない。ログインHTMLやPDF以外の応答はPDFとして取り込まない。別の配布元で認証が必要な場合や取得できない場合は、そのサイトで閲覧・保存して通常のファイル選択から開ける。

## 添付先と状態の保護

添付先はCSSセレクターを再実行して探し直すのではなく、選択時の実DOM要素に結び付ける。元タブ、文書トークン、ジョブID、拡張自身の記入画面URL、記入タブのクライアントIDを照合する。タブIDが渡るブラウザーでは、その値も照合する。

元ページの移動、欄の置き換え、選択ファイルの変更、acceptやmultipleの変更、フォームや送信先・送信ボタンの変更は、そのまま別の宛先に追従せず止める。PDFの回答は記入タブに残す。複数ファイル欄では他の添付を保ち、選択した元PDFだけを置き換える。

書類・回答・フォームの入力値をストレージへ保存しない。通常の入力値は拡張へコピーしない。選択されたPDFと出力PDFだけを、認証したcontent scriptと記入タブの間で受け渡す。元タブが残れば、サービスワーカーの再起動後も続行できる。

## 提出と完了の意味

通常サイトの送信操作は既定で無効。送信ボタンが一意に決まる場合だけ、そのボタン名を表示して利用者が選べる。標準の[requestSubmit](https://developer.mozilla.org/en-US/docs/Web/API/HTMLFormElement/requestSubmit)を使い、サイトの検証・submitイベント・submitterを維持する。form.submitで検証を飛ばさない。

| 結果 | 表示する事実 |
| --- | --- |
| attached | 選んだ欄に記入済みPDFを設定した |
| needs-input | PDFは添付したが、元フォームに入力不足などがある |
| submission-requested | 指定したフォーム操作を行った。サーバーの受理は未確認 |
| submitted | サイト用アダプターが定義した完了画面を確認した。現在この結果を返すのはローカルの模擬提出だけ |

一般サイトを一律に「提出完了」「受理済み」と表示しない。アダプターの追加時は、適用先、確認画面・認証の扱い、完了の証拠、再試行時の重複防止をそのサイトごとに定義する。

## 現在の対応範囲

- サイトアクセスを許可したHTTP(S)ページのトップ文書。通常のPDFリンク、MIMEまたはdownload名で示されたPDF、埋め込みPDF、選択済みPDFに対応する。
- 標準のinput type=fileへの添付。[filesの標準プロパティ](https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/files)とDataTransfer、input／changeイベントを使う。
- ブラウザー組み込みのPDFビューアー、権限のない配布元、別フレーム内だけのフォーム、閉じたShadow DOM、File入力を持たない独自アップローダー、信頼済みイベントを要求するサイトには、この実装だけで一律対応したと扱わない。
- PDFの解析・記入精度は既存エンジンの制約に従う。図書館原本の14項目（手続の内容の6つのチェック欄を一問にまとめ、文字入力13項目と合わせる）はSHA-256一致時だけの記入位置設定で、今回の汎用的なPDF検出とは独立する。

## 実装と検証

上記の責務で実装済み。型検査、全41ファイル465テスト、Gecko・Chromiumのビルドとパッケージ検査が成功した。Mac版Chrome 156で、専用連携のない通常フォーム・別オリジンのPDF・複数添付先・他の添付の保持・標準入力検証・送信操作の選択・元サイト変更時の停止を確認した。同一オリジンのセッション維持と、別配布元への認証Cookieの省略も確認した。Floorpの今回の実機検証は含めない。終了処理タイムアウトと再検証の履歴は、リポジトリの `docs/specs/3.0.0/implementation-status.md` に残す。
