# 赤羽台祭向け Silver Guide 利用者試験キット

**状態：準備資料。実ユーザー試験は未実施。** 赤羽台祭での実施予定があるが、現在は実施できない。日時、会場、参加者、運営責任者、同意手続き、記録の保持期間は未確定。本書の作成による募集・予約・第三者への連絡は行っていない。

基準は[品質と配布仕様 §6](specs/quality-and-release.md#6-アクセシビリティと利用者試験)。操作の確認方法は[使い方](user-guide.md)、既存の機能確認は[検証記録](verification.md)を参照する。以下は試験の提案であり、達成済みの結果ではない。

## 1 試験の構成

- 対象利用者を最低12人。60歳以上を含め、行政文章やPC操作に慣れていない人の困り方も記録する。年齢は任意の区分だけで扱う。
- 別途、キーボード・読み上げ等を常用する人を最低4人。同じ人を両群へ重複計上しない。支援技術の種類と経験を分けて記録する。
- 1人に5課題と保存・再開を行う。所要時間は通常40～50分を目安とする提案。支援技術の設定・休憩には別の時間を設け、操作速度だけで評価しない。
- 展示の短時間体験、運営者の予行、サブエージェントの検証は本試験の人数へ数えない。一部課題だけの実施はその範囲を明記する。
- 進行役と観察役を分ける提案。参加者は使い慣れた入力方法を選ぶ。思考の発話は任意とし、発話しないことを失敗にしない。

利用者試験で見つかる問題とWCAGの基準確認を組み合わせる。少人数・特定の支援技術の結果を全利用者へ一般化しない。[W3C WAI: Involving Users in Evaluating Web Accessibility](https://www.w3.org/WAI/test-evaluate/involving-users/)

## 3 試験端末と架空資料を準備する

通常利用のブラウザープロファイルを使わず、試験専用の環境を用意する。拡張機能の版・パッケージ識別子、OS、ブラウザーと版、画面寸法、文字サイズ、ズーム、支援技術、音声の有無を記録する。初回はFloorpを基本とする提案で、実際の環境は実施前に固定する。

開発リポジトリーで依存関係と実行資源を準備した後、PDFを生成する。未取得なら `corepack pnpm@10.13.1 run assets:download` を先に実行する。試験時に参加者の入力を含む外部資料を取得しない。

```powershell
Set-Location E:\floorp-browser-dev\silver-guide-extension
node scripts/create-qa-fixtures.mjs E:\others\silverguide-qa\akabanedai\fixtures
```

このスクリプトの引数は出力先1つだけで、追加のフラグはない。`native-form.pdf`（元から入力欄がある）と `text-form.pdf`（文字と枠だけ）の2ファイルを作る。開発用の `public/assets/fonts/NotoSansCJKjp-Regular.otf` が必要。画像PDF・混在PDFを生成した扱いにはしない。

両PDFの正解欄は氏名・ふりがな・住所・電話番号の4つ。下の署名説明や注意文は回答欄に数えない。生成した元PDFとハッシュ、期待する4欄の位置、試験に使う版を運営用に保存する。スキャンの追加課題は、この架空資料を画像化した別ファイルを事前に目視確認して用意できた場合だけ行う。

## 4 参加者へ読む説明案

「Silver Guideの分かりにくい点を探す試験です。あなたの能力を評価するものではありません。架空の情報だけを使います。分からないときはそのまま教えてください。休憩や中止を選べます。参加しないことによる不利益はありません。記録する内容、見る人、保存期間、削除の申し出方法は、こちらの説明票にあります。」

説明票には実際に決まった責任者・窓口・保持期間を入れる。観察への同意と、録画・録音・発言引用への同意を別々に確認する。録画は既定で行わず、同意を確認できた範囲だけ記録する。参加者の顔や私物端末の通知、パスフレーズが映る記録を避ける。

開始前のチェック：説明を確認／参加同意／記録範囲の選択／任意の年齢区分／普段の入力方法／休憩方法。氏名や連絡先を観察票へ入れない。対応表を作る必要があるかは未確定で、作る場合は観察票と分けて管理し、匿名化済みとは扱わない。

## 5 五つの課題カード

参加者には「課題文」だけを渡す。成功条件やボタンの場所は進行役用。操作の練習は別の短い資料で行い、試験課題の解き方は教えない。

| ID | 課題文 | 進行役が照合する成功条件 |
| --- | --- | --- |
| T1 PDF | 「この架空の申請書に、カードの情報を記入してください。元の用紙と比べ、保存した書類をもう一度開いて確認してください。」 | 4欄の意味・記入者・位置を確認。氏名等が正しい枠に入り、注意文を欄にしない。保存された実PDFの日本語・全回答を確認できる。保存を申請の提出と誤認しない。 |
| T2 読む | 「この案内を読みやすくして、対象になる人と受付の期限、受付方法を見つけてください。」 | 見出し・リスト・表の見出しとセルを辿れる。18歳以上、試験区、11月30日17時を原文と一致して答える。文字調整後も操作できる。音声を希望した場合は本人の操作で再生・停止できる。 |
| T3 説明 | 「『委任状』の意味と、どんな場合に必要なのかを確かめてください。説明の元になった文章も示してください。」 | 説明と原文を対照でき、代理人の場合に必要／本人の場合は不要を取り違えない。説明できない部分を確定情報と思わず原文で確認する。原文だけの表示を説明成功に数えない。 |
| T4 準備 | 「試験用の本人確認カードは準備済み、委任状はまだです。準備の記録を作り、委任状を後で確認する状態にしてください。申請を提出した記録にはしないでください。」 | 個人用チェックリストを作り、準備済み・保留・未着手を区別できる。チェックを取り消せる。架空の準備記録を公式の制度案内と思わない。 |
| T5 ウェブ | 「架空ページの氏名・住所と連絡方法を、見やすい作業画面から入力してください。反映する内容を確認し、元ページで結果を確かめてから戻してください。送信はしません。」 | 対象フォーム・現在値・候補を確認して本人が反映する。氏名・住所・電話の選択が正しい。パスワード・同意を反映対象にしない。取消で元の値へ戻り、提出済みとは表示されない。 |

T1は `native-form.pdf` を全員の共通基準とする提案。追加の `text-form.pdf` と低品質スキャンは別枠で結果を記録し、通常PDFの成功率へ混ぜない。原画像の意味を独力で確認できたか、操作部品にアクセスできたかも分ける。

**全員の保存・再開課題（T1またはT5の続き）：**「この作業を途中保存し、作業タブを閉じてから、同じ試験端末で続きを開いてください。」原本・回答・確認状態が同じこと、未保存と保存済みを区別できることを照合する。設定や変換を使った場合は、その記録も保たれるか確認する。

**時間と同意がある場合の追加課題：** 暗号化バックアップを保存し、別の空の試験保管庫へコピーとして取り込み、作業を開く。運営者が試験専用の復元環境を用意してから行い、今の保管庫や端末の実データを削除しない。未実施を復旧成功へ数えない。

**低品質資料の追加課題：** 読めないラベルや不足した欄を原本と比べ、修正または保留する。OCRの文字誤り、ラベルとの誤対応、検出漏れを別々に記録する。意図的に作った誤りは「仕込み」と明記し、実解析の誤りへ数えない。

## 6 支援の段階と中止

| 段階 | 進行役の対応 | 集計 |
| --- | --- | --- |
| S0 | 課題文と架空情報だけ。アプリの操作を助言しない。普段のAT設定は開始前に整える。 | 独力完了 |
| S1 | 課題文の再読、中立の確認「いま何を探していますか」。操作場所を教えない。 | 直接指示なし。S0と分けて記録 |
| S2 | 機能や場所のヒント「作業一覧を見てみてください」 | 支援あり |
| S3 | 操作を具体的に指示する、操作を一度示す | 直接支援あり |
| S4 | 進行役が代行する | 本人完了へ数えない |

開始・終了時刻、最も強い支援段階、支援を出す前の停止地点を残す。参加者が希望したら支援する。目安時間を超えただけでAT利用者を失敗にしない。疲労、中止希望、実データの混入、誤送信や保存済みデータ喪失のおそれがある場合は中止し、原因を分けて記録する。

## 8 集計と試験後の扱い

- 通常PDFの設計目標は、90%以上がS0・S1で正しい保存を完了すること。本人が誤配置・欠落に気付かず完成としたものは誤完了とする。人数・分母・S0/S1内訳・誤り・支援を併記する。
- 一般群とAT群、PDF種別、5課題、保存再開、追加backupを分けて報告する。人数と95%信頼区間の算出方法を残す。少人数の比率は探索結果で、精度校正や全利用者への保証には使わない。
- 試験開始した課題の失敗や製品都合の中止を成功率から黙って除かない。未実施、環境準備不足、参加辞退・記録撤回は別に記録し、集計への扱いを説明する。
- データ喪失、無断の外部送信、記入者・配置の取り違え、主要操作を妨げるアクセス障害は件数が少なくても個別に扱い、[品質仕様の公開条件](specs/quality-and-release.md#1-合否の原則)へ戻す。
- 修正候補を影響・再現性・支援の程度で並べ、担当と再試験の課題を記録する。参加者の発言と運営者の推測を混ぜない。
- 終了時に試験保管庫・ダウンロード・バックアップ・ブラウザー履歴等の残りを確認する。保管する観察票・証拠と削除する生成物は、確定した同意と保持方針に従う。保持期間を本書から推測して決めない。

このキットを整えたこと、予行が成功したこと、利用者試験が完了したことは別々に記録する。赤羽台祭での結果が得られるまでは、対象利用者試験の公開条件を未完了のまま保つ。
